## ScrapeDo usage
- **None.** All requests (homepage, brand page, listing page, detail pages) go through `BrowserService.startBrowserAndStaticVisitUrl` (free). Initially fixed with ScrapeDo for the homepage only (REGULAR/1cr), but a follow-up test showed a plain browser visit passes DataDome on the homepage too, on the first try, with no retries — so ScrapeDo was removed entirely. If DataDome starts blocking the browser path again in the future, re-add a ScrapeDo branch for whichever request starts failing (see git history on `bugfix/MAR-2132-fix-e-motors-FR-parser` for the ScrapeDo-based version to restore).
- See `crawler-estimate-credit-cost` run from 2026-07-13 (last healthy day 07-06/07): B&M ~1,951 req/day, Listings ~913 req/day at REGULAR tier if ScrapeDo were used for everything — kept here as a reference ceiling, but the actual fix needs 0 credits/day.

- **2026-07-15** — **Site-side pagination is broken, capping every model at page 1 (~12 vehicles), regardless of real stock.** Follow-up on the entry below: the initial "Audi/Renault match the site" read was only true because those brands' individual models mostly have ≤12 versions each, so page 1 already captured everything — it masked a real, severe bug that surfaced on Peugeot (high-volume models). Confirmed via direct browser navigation (independent of our crawler) two separate site-side breaks: (1) the static `.next-cars` "Voir plus de véhicules" link is mistemplated — truncates the model slug (`peugeot-208` → `p-2`, `peugeot-boxer-fourgon` → `p-b`, `peugeot-5008` → `p-5`) and 404s on the site's own domain; (2) the real infinite-scroll backend the site's own JS calls (`GET /liste-de-nos-vehicules/page-2?marque[]=peugeot&order-by[]=dispo_asc`, discovered via network tab while manually scrolling) returns a straight **500 Internal Server Error** — confirmed broken for real site visitors too, not just us. `POST /car-list.json` also exists (405 on GET, so POST-only) but wasn't tested further once (2) confirmed the outage. Concrete case: Peugeot 5008 states **"215 véhicules"** on-page, we only reach 12 (page 1), and joining `vehicle_visit` (today, `lastVisit >= CURDATE()`) against ES via `md5(URL)` shows only **7 distinct vehicles actually confirmed today** for that model. No workaround exists on our side — neither the real model slug nor a `?page=2` query string reaches genuine page-2 content, both just re-serve page 1. Not a regression from our 07-14 fix; it's an independent site-side outage. Re-check periodically in case the site fixes their own pagination infra.
- **2026-07-15** — After the 2026-07-14 URL-restructure fix deployed, spot-checked Audi (61 in ES vs ~60 on site summed across all 3 condition pages) and Renault (557 in ES vs ~513+ on site) — both appeared to track the live site closely. **Superseded by the pagination-bug entry above** — this only held because Audi/Renault's individual models mostly have ≤12 versions each. Separately, the ~2,832 active vehicles sitting in ES are inflated by **stale docs protected by the deactivation lock**: e-motors was locked during the ~week-long 0-vehicle/URL-restructure regression (07-09 to 07-13, see below) so nothing deactivated while the crawler found 0 new vehicles. `vehicle_visit` shows today's crawl (`todayCount`) only revisited **49.51%** (`ratioPercent`) of yesterday's active set (`prevCount` 1,521 vs `todayCount` 1,551) — meaning roughly half of the currently "active" e-motors vehicles are actually gone from the site and would deactivate the instant the lock is lifted. **Do not simply unlock deactivation** — a ~50% single-night drop would very likely trip the mass-deactivation safeguard again and re-lock the site, creating a cycle. Instead, deactivate the stale ~50% manually (batch, outside the automated nightly run) before removing the lock, so the lock doesn't immediately re-trigger.
- **2026-07-14** — Second regression, hours after the 2026-07-13 browser-request fix was verified: site removed the combined `/mandataire-{brand}` page (brand alone now 500s with the site's own branded 404 page). First fix attempt built `listingUrl` as `/mandataire-{brand}-{condition}-{model}` — logically consistent with "the brand page moved to condition-specific URLs," but wrong: this 3-segment URL doesn't exist on the site (confirmed via direct browser navigation - it 404s, e.g. `/mandataire-renault-occasion-clio` has 0 results despite Clio having real stock). Found the real pattern by following the site's own "Voir les versions" link from `/liste-de-nos-vehicules?marque[]=renault`, which resolves to `/mandataire-renault-clio` (brand+model, no condition) - the site kept this combined (all-conditions) page even after removing the brand-only combined page. Fix: use condition pages (`-0km`/`-occasion`/`-utilitaire`) only to discover the model dropdown, dedupe by modelId across conditions, build `listingUrl` from the plain brand+model slug. Verified via `crawler-test-flow`: 37/39 Renault listing pages returned real vehicles, 58+ indexed in local ES. Lesson: when a site's URL structure changes, don't assume the new URL taxonomy applies uniformly everywhere in the hierarchy - check the site's own internal links (e.g. a "view all" or "see versions" button) rather than pattern-matching from one broken example.
