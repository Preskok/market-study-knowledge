## Site architecture (as of 2026-07-09)
- **Brands**: `GET https://core.polovniautomobili.com/api/v1/brands/active/category/{car|van}/search-domain/detailed-search` → `{"brands": string[]}`. `car` = passenger, `van` = commercial (`/kombi-i-laka-dostavna-vozila`).
- **Models**: `GET https://core.polovniautomobili.com/api/v1/models/active/brand/{brand}/category/{car|van}/search-domain/detailed-search` → `{"models": string[]}`. Note: for brands with "series"/"class" naming (BMW `Serija 3`, Mercedes `A Klasa`, etc.) the array mixes coarse group headers with their individual sub-models. Confirmed live: filtering by a group header returns 100% duplicate vehicles (`model[]=A Klasa` → 724 results, zero with `model` field literally `"A Klasa"` - all A140/A150/.../A250; `model[]=Serija 3` → 1,759 results, same pattern, zero literal `"Serija 3"`). No API field or universal string pattern distinguishes a group header from a real model ahead of time (Mercedes shares a text prefix with its submodels, BMW doesn't). Fixed in `getVehicleListPageResponse`: still visit the group-header listing (unavoidable), but skip saving any item whose own `model` field doesn't match the searched model - the vehicle gets correctly saved once, by its own real model's crawl unit.
- **"Ostalo"/"other" catch-all brand/model has an internal naming split, and the brand side was silently broken.** The catalog API lists the catch-all as `"Ostalo"` (Serbian) for both brands and models. The value **stored on the vehicle itself differs by field**: `item.brand` is `"Ostalo"` (matches the search term), `item.model` is `"other"` (does not match - different string, different language). Registered both variants in `OtherBrandAndModelsValues.ts` (`AdCrawlingSitesOtherModelValues['polovni-automobili'] = ['ostalo', 'other']`); the brand list only needed `['ostalo']` since `item.brand` already matches. The group-header duplicate filter uses `CrawlerHelper.isModelUnknown` on both sides (not raw string equality) specifically to survive this mismatch.
  - **`brand=Ostalo` is broken on the `_next/data` JSON route specifically.** The pretty HTML page 308-redirects `brand=Ostalo` → `brand=other`, but `_next/data/<buildId>/sr/auto-oglasi/pretraga.json?brand=Ostalo` does NOT follow that redirect - it returns `{"pageProps":{"__N_REDIRECT":"/auto-oglasi/pretraga?brand=other&sort=basic",...}}` with no `searchResults`/`paginationBaseUrl` at all. Fetching with `brand=other` directly works correctly (9 vehicles, `paginationBaseUrl: "/auto-oglasi/pretraga?brand=other"`). `getBrandsForCategory` now detects this brand via `CrawlerHelper.isBrandUnknown` and uses `other` as the literal query value.
  - **The catch-all brand's models list is always empty** (`GET .../models/active/brand/Ostalo/...` and `.../models/active/brand/other/...` both return `{"models":[]}`) - there's no model dimension to iterate. Without a fix, the crawler's default "no models found for brand, skip" guard would silently drop this brand's entire inventory from every crawl, forever, with only a low-visibility warning log. Fixed: push a single brand-only `ParseVehicleParams` for this one brand (no `modelName`), matching the "site genuinely has no model-level filter" exception in crawler-create §6.
  - **Model-side `model[]=Ostalo` does NOT have the same JSON-route breakage** - confirmed live (`brand=Renault&model[]=Ostalo` → 2 correct results, `paginationBaseUrl` self-corrects to `.../model[]=other`), so no query-value translation was needed for the model dimension, only for brand.
- **Listings & pagination**: fetched via `https://www.polovniautomobili.com/_next/data/<buildId>/sr{path}/pretraga.json?brand=X&model[]=Y&page=N&sort=basic` instead of the full HTML search page - same `pageProps.searchResults` shape as before, plus `pageProps.paginationBaseUrl` (the pretty `/auto-oglasi/pretraga?...` url minus `&page=`) used to reconstruct the stored `VehicleListUrl` so persisted data never contains the buildId path.
- **Detail pages**: `parseVehicleInput`/`parseDealer` share one fetch (base class calls `fetchRequest(parseVehicleParams.url)` once); the crawler transparently rewrites the pretty `/auto-oglasi/{id}/{slug}` url to `_next/data/<buildId>/sr/auto-oglasi/{id}/{slug}.json` inside its `fetchRequest` override, so `AdVehicle.url` stays the human-facing ad url while the actual fetch is the ~4x-smaller JSON (60KB vs 242KB for a sample ad).
- **buildId**: Next.js build id (e.g. `build-TfctsWXpff2fKS`) changes on every site deploy - never hardcode it. Resolved from the homepage's `<script src=".../_buildManifest.js">` tag (regex `_next\/static\/([^/]+)`), Redis-cached 1 day (`CacheKeysEnum.POLOVNI_AUTOMOBILI_BUILD_ID`), and re-normalized on every `_next/data/` fetch attempt (so a mid-crawl deploy self-heals on retry via `isResponseNotFound`/`isBadRequest` overrides detecting the `{"pageProps":{"pathname":"/404"}}` stale-buildId body shape).
- **Detail URL slug is decorative only, not validated server-side.** Verified live: `_next/data/<buildId>/sr/auto-oglasi/29810161/x.json` (deliberately wrong slug `x`) returned a full valid 200 with the correct `productData` - the JSON data route resolves purely by the numeric id, the slug segment is never checked. So a slug that doesn't byte-match the site's own generated slug is a cosmetic imperfection, not a broken/wrong-vehicle bug.
- **Currency confirmed EUR.** Live sample: `priceCurrency: "€"` on both listing and detail JSON. No RSD-priced listings observed - `price`/`discountedPrice` (not `original*`) is the correct EUR-site price family per crawler-create §8.
- **EV battery fields exist only on the detail JSON, not the listing.** `productData.batteryCapacity` (kWh) and `productData.fullBatteryRange` (km) are present for electric vehicles (verified live on a Tesla Model 3: `batteryCapacity: 75`, `fullBatteryRange: 500`) but absent from `SearchResultItem` on the listing route - map these on the detail side only.
- Dealer page URL = `${baseUrl}/${contactDetails.urlAlias}` (not a `/prodavci-vozila/...` path).
- VIN field not exposed anywhere in the JSON - genuinely unavailable.
- Chassis/body-type dictionary (Serbian display text): `Kupe/Džip/SUV/Limuzina/Hečbek/Karavan/Monovolumen (MiniVan)/Kabriolet/Roadster/Pickup/Van` (passenger) + `Ambulantni kombi/Dostavni kombi do 3.5t/Dostavni kombi preko 3.5t/Hladnjača/Putar/Putnički kombi/Autotransporter` (commercial).
- **`productData.damaged` free text - never treat as "any text = damaged".** Value is a full Serbian sentence, not an enum: `"Nije oštećen"` (not damaged) legitimately contains the substring `"oštećen"` (damaged), so a plain `.includes('oštećen')` check flags every undamaged vehicle as damaged. Real damaged values are `"Oštećen - u voznom stanju"` / `"Oštećen - nije u voznom stanju"` (matching the old HTML crawler's exact-match allowlist). Fix: `!rawIsDamaged.toLowerCase().includes('nije oštećen')` - matches the negated phrase itself, correctly `true` (damaged) for both real damaged values even though the second one also contains "nije" elsewhere in the sentence.
- **Commercial vehicles need the commercial path prefix on their detail url, not the personal one.** `getVehicleListPageResponse` was hardcoding `personalVehiclesUrlPath` for every vehicle's `url`/detail fetch regardless of which category (`/auto-oglasi` vs `/kombi-i-laka-dostavna-vozila`) the listing actually came from - every commercial vehicle (vans, trucks) got a broken url that redirects to the search page when visited (confirmed live: id `28802083` "Mercedes Benz Sprinter 313 cdi." 404s/redirects under `/auto-oglasi/...` but resolves correctly under `/kombi-i-laka-dostavna-vozila/...`). Fixed by deriving the correct path from `pageProps.paginationBaseUrl` (which already reflects the real category) instead of hardcoding. `resolveUrl`'s detail-page regex/rewrite also needed to accept either path prefix, not just the personal one - it would otherwise fail to recognize (or mis-rewrite) a correctly-built commercial url.

## History & quirks (newest first where known)
- **2026-07-13** — `the storeId-drift verification method` run against stage found real storeId drift, driven by two compounding bugs in the current URL/slug construction (this **updates/corrects** the 2026-07-10 entry below, which called the "(може zamena)" slug mismatch purely cosmetic - it is NOT cosmetic for identity purposes, only for site routing):
  - **"(може zamena)" bracket bug** - `StringHelper.slugify()` only lowercases + replaces spaces with dashes; it never strips parentheses or diacritics. 78/100 (78%) of a stage sample had "zamena" baked into the stored `url`, always wrapped in literal parens with the accented `ž` kept (e.g. `bmw-420-d-m-sport-(може-zamena)`). Live-verified against the real site: the actual canonical slug is plain ASCII with no parens (`moze-zamena`, confirmed via `29820989/opel-crossland-x-12-at-moze-zamena` and listing hrefs), and the site's own `<link rel="canonical">` for a "moze zamena" ad (`29492979`) **drops the suffix entirely** rather than keeping it bracketed.
  - **`attp` query param on old prod URLs is not static** - same vehicle id `28652756` has two prod records a day apart with different `attp` values (`p0_pv0_pc0_pl1_plv0` vs `p1_pv0_pc1_pl1_plv0`). This means storeId continuity for this site was already fragile pre-rewrite (every re-crawl with a different `attp` produced a new storeId even under the old crawler), and a "convert new→old URL" service can never reconstruct it - it can only be stripped away going forward.
  - Old prod URLs **do** occasionally carry "zamena"/"moze-zamena" (416 / ~2.47M docs contain "zamena" anywhere, only 25 contain the fuller "moze-zamena" phrase) but **0 ever contain a literal parenthesis** - confirming the bracket-wrapping is new to this rewrite, not something the site or old crawler ever produced.
  - "zamena" is not always a clean trailing suffix - some real titles have more text after it (`gle-350-zamena-kredit`, `mazda-6-zamena-za-suv`, `mazda-6-zamena-pickup`, `c-350e-zamena-kredit`, plus a typo variant `zamenaa`). Any fix must truncate from `-zamena`/`-moze-zamena` onward rather than matching only those two exact literal suffixes.
  - **Proposed fix (not yet implemented):** build `legacyUrl` by (a) stripping query params, (b) truncating the slug from `-zamena`/`-moze-zamena` onward; keep the current raw `url` as `workingUrl`; apply the same two rules in the MAR-1975 old-URL conversion service for historical prod URLs.
