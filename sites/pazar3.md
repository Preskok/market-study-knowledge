🟡 **2026-07-16 STILL FLAPPING, ROOT CAUSE NOW PRECISE.** Recurring intermittent 0-vehicle days (07-01, 07-02→07-03, 07-06, 07-16) each triggering a deactivation lock and self-recovering via manual unlock — pattern recurs on a roughly 2-3 day cadence. The mechanism is now confirmed precisely (see 2026-07-16 entry below): the site occasionally serves an alternate SEO/lite template for `/ads/vehicles/automobiles/for-sale` that omits the entire `.groups-count` brand-facet widget (not an unfilled shimmer — the DOM subtree is absent). That response gets cached (`statusCode:200`, looks legitimate) and replayed all day since S3 cache is checked first even on retry. No code fix needed — operational: delete the poisoned prod S3 key (`AWS_PROFILE=<prod-profile> aws s3 rm`, NOT the read-only `AMS_S3_PROD_*` .env creds) + rerun on prod.

- **2026-07-16** — Alert "Prepared listingUrl messages 0" at 05:00 UTC. Root-caused precisely: the poisoned S3 daily-cache key for `/ads/vehicles/automobiles/for-sale` (today's key, written 2026-07-15T22:05:50Z) is a legitimate `statusCode:200` response with correct title, correct category selected, and 53 real `row-listing` ads — but the site served an **alternate page template** for that one request. Confirmed via structural diff against a known-good fetch: in the good page, right after the breadcrumb (`</ul>`) comes the `groups-count-shimmer` placeholder then the real `<div class="groups-count ...">` brand-facet widget (all ~70 brands + counts, e.g. `Audi, 9030`); in the poisoned page, the breadcrumb is immediately followed by a `<div class="shortDescription visually-hidden">` SEO filler paragraph instead — the entire brand-facet DOM subtree is absent, not just an unfilled shimmer. This is the same site-serves-alt-template signature as the 07-02→07-03 incident, now confirmed precisely rather than inferred. Failing selector: `.groups-count a` in `getBrandsAndModels()` — selector itself is correct, it just matches 0 elements against this one substituted template. Fixed operationally: deleted the poisoned key from prod S3 via `AWS_PROFILE=<prod-profile> aws s3 rm` (the read-only `AMS_S3_PROD_*` creds in `.env` correctly refused the delete — expected, use the AWS CLI profile instead). **Important:** initial investigation nearly proposed a redundant code fix (adding `/for-sale` to the URLs) — turned out `getBrandsAndModels()` has fetched `/for-sale` since 2026-05-04 (`21df32f7f3`, Matea Lencek, `MAR-2039`) and is already on `develop`/`master`; the local branch used for investigation was 3082 commits behind `origin/develop` and hadn't been fetched, making already-fixed code look unfixed. Always `git fetch origin develop master` before assuming a symptom means the deployed code lacks a known fix.

Different root cause from the 07-01 incident. Pulled the prod S3-cached daily response for the for-sale URL: `statusCode 200`, real 987KB body, correct title, listing content intact (53 `row-listing` items, pagination present) — but `.groups-count` (the brand-facet selector `getBrandsAndModels()` reads) appears 0 times anywhere in the body. Conclusion: a bad/anomalous response got cached in S3 for that date and is being replayed on every read since (`useS3Cache: true`). Fix is operational (delete the S3 key + rerun), not code.
